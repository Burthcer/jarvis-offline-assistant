## 1. What the owner wants
His words (2026-11-02), shortened:
- "I don't need it to be as smart as GPT. I just need it to do the stuff I'm too lazy to do, like searching something up. Not smart in code, but in understanding what I'm saying and turning it into the right action."
- "If it's a rebuild, make it a really, really good rebuild. We're planning for the future: more features, more capabilities."
- "Ideally something like a Hermes agent that learns and tracks what I do and how I do it."

My reading, confirmed by the owner on 2026-11-03 (he means Nous Research's Hermes Agent: keeps a memory and learns from use):
1. Understands what he MEANS from loose or mis-heard speech, including follow-ups ("do that again", "the second one").
2. Does the right thing reliably, and says truthfully what it did.
3. Feels aware: knows the time, what's open, what's playing, what's on his lists, what was just said.
4. Remembers and learns: his words and nicknames, mishearings, usual apps and times, corrections, facts, routines. All local, visible and deletable.
5. Easy to grow: a new ability is one small piece of code, not new patterns in five files.

Not goals: writing code, ChatGPT-style general knowledge, online AI (parked), phone relay, Mac mini server, reading or clicking the screen (future: first Windows accessibility, later vision; leave a slot for it).

## 2. Why a rebuild, and why not from zero
V1 was built one complaint at a time, so it is a pile of special cases:
- `jarvis/actions.py` (~820 lines) and `core.py` (~250) are hand-written patterns. The AI (`brain.py`, ~300 lines) only rewrites speech into the exact command text those patterns accept. No pattern means no ability. A name misheard with another first letter ("prome" for Chrome, "jamin" for Gemini) is refused.
- `voice.py` (~760 lines) is a stack of patches on the listening loop.
- The AI sees the last 2 exchanges and nothing else. No memory between sessions. Replies are fixed sentences the AI rewords.
- So it feels hard-coded, and every new phrasing needs a new patch.

Not from zero, because these are solid and tested: the insides of the abilities, timers/reminders/notes (`store.py`, `timeparse.py`), the window and the pill (`ui.py`, `island.py`, `web/`), settings, the speaking voice, the tests (75,000+ rule checks, 20,000+ action checks, window and logic tests), and the models.

## 3. Keep / rebuild / not now
KEEP (wrap them, don't rewrite): ability insides (open/close apps, tab closing, screenshots, folders, timers, reminders, notes, time parsing), window + pill + tray, settings, speaking voice (Kokoro, Piper fallback), `make_app.py` + desktop shortcut + one-copy lock, the models (read-only from Wisperno's folder), tests, local logs.
REBUILD: the listening front end, the understanding layer, the command front door (patterns), replies. NEW: context awareness, memory and learning, the evaluation harness.
NOT NOW (CLAUDE.md): online switching (but keep the model swappable behind one small interface), phone relay, Mac mini server.

## 4. Design
```
Ears (hands-free mic) -> Understanding (AI picks abilities) -> Safety check -> Abilities -> Reply (AI words the real result)
        Awareness (clock, apps, tabs, media, lists) -> Understanding        Memory (local) <-> Understanding, Abilities
```

### 4.1 Ears
- Hands-free "Jarvis" is the main way in and comes first. Hold-a-key is an optional extra for later (13.2 decision 4).
- One clean listening loop: ring buffer with pre-roll, voice detection, end of sentence from adaptive silence, the WHOLE sentence goes to the recogniser. Keep: not hearing its own voice, following the Windows default mic and speaker (earphones).
- Recogniser: same faster-whisper large-v3-turbo (int8_float16) unless Phase 1 says otherwise. Bias it with a live vocabulary from the catalog (apps, sites, bookmarks, words in his notes). Word confidences (faster-whisper can give word probabilities, check the installed version) so a low-confidence word triggers "did you mean...?" instead of a wrong action.
- Music on the speakers: measure first. Options (unproven): cancel what the PC is playing using Windows loopback capture, or lower the volume while listening. This may need a different audio library.
- Output: text, word confidences, how it was triggered, a clip id for diagnosis.

### 4.2 Awareness
A small "snapshot" built on demand: date, time, weekday; running apps; the foreground window; browser tab titles (Windows accessibility); what's playing (Windows media session: which app, title, playing or paused); timers; reminders; the last few turns; the last things mentioned (app, tab, timer, note); the memory profile. "What's the time", "what's the date", "how many reminders" are answered exactly from this, never guessed by the AI.

### 4.3 Understanding (the resolver)
- Input: sentence + snapshot. Output: a list of ability calls with arguments, or a short question, or plain conversation.
- The AI picks from the registry (name, one-line description, a few examples each; show only the most relevant abilities to keep the prompt short). Force the output into a fixed JSON shape: llama.cpp can constrain generation to a schema; check that the installed llama-cpp-python 0.3.26 supports it.
- Entity matching is separate from the AI: app, site, bookmark, tab and file names are matched against the live catalog by SOUND and spelling (phonetic + fuzzy, no first-letter rule), with his usage history as the tiebreak. Confident: act. Two close candidates: ask a short question. None: say what it heard and offer the nearest.
- Several actions in a sentence ("open WhatsApp and close Edge") are several calls, each with its own ability. Follow-ups are resolved from the last things mentioned.
- Fast path: obvious commands skip the AI (pause, mute, volume 50, what's the time). Each ability declares example phrases that are matched cheaply, from the same registry, not a separate pile of patterns.
- Model: Llama 3.2 3B Q4 today. Phase 1 compares candidates on his real sentences (for example Qwen2.5 3B; Wisperno's own benchmark folder compared a few, for a different task). Tell the owner before any download.
- Honest ceiling: a 3B model will still make mistakes. The design makes mistakes cheap: confirm risky actions, ask when unsure, never fake success.

### 4.4 Safety
Each ability has a risk: safe (just do it), confirm (ask first: delete, send, overwrite), never (command line tools, PowerShell, registry, uninstallers, shutting down the PC, changing system settings). The registry IS the allowlist: nothing outside it can run. Log every executed action locally. Undo where it is possible (deleted reminder, timer).

### 4.5 Abilities
One small module each: name, description, typed parameters, examples, risk, `run(args, snapshot)` returning a Result `{ok, facts, details}`. The Result is what the reply reads. To port or build (from V1 and the checklist): open/close/focus any app; tabs (open N, close first/second/last/this/all); websites, bookmarks (Edge and Chrome keep them in a local file), files by name; search (Google by default; a site or browser only if he names it); media through the Windows media session (play, pause, next, previous, without bringing the tab forward; likely, verify with YouTube in Edge and with WhatsApp in front); YouTube page actions; volume (system: full, max, N, up, down; one app's volume through Windows per-app audio, for example the pycaw library, a candidate); timers (several, by length, pause/resume/cancel); reminders (create, change in place, cancel by day); notes (spoken emails: "at the rate" is @, "dot" is "."; recall; forget); time/date/day; screenshot to clipboard; folders; shutting Jarvis down; alerts on the pill. Each has unit tests with a fake OS.

### 4.6 Reply (narrator)
After the action, the AI writes one short reply from the Result facts only, in the persona: calm British butler, dry wit, "sir", never the owner's name, varied. A checker rejects wording that changes a name or number, flips the meaning, or claims something not in the facts; then a plain true sentence is used. Lists and goodbyes stay exact. Never let the reply prompt silently overflow the model's memory (V1 did): log errors, test prompt sizes.

### 4.7 Memory and learning
Local SQLite in `data/`: events (time, what he said, what was heard, ability and arguments, result, success, his correction); facts (what he told it); aliases (heard word to real name, with counts); usage (per app, site, ability: counts, last used, time of day); routines (steps he taught). The AI rewrites a short "what I know about the owner" profile (about 200 words) now and then from these; it goes into the resolver's context.
Levels, in this order:
- L1 Log every turn and outcome.
- L2 Corrections and aliases: "no, I meant..." stores the alias; usage ranks ambiguous matches. Learn only from explicit corrections or repeated confirmed success, so a mishearing isn't taught as a name.
- L3 Facts and preferences: notes, "I usually...", spoken emails, names.
- L4 Habits and suggestions: notices repeated times and sequences and OFFERS ("shall I...?"). Never automates without being told.
- L5 Teachable routines: "when I say study mode, open X, set a 25-minute timer..." stored as a sequence of abilities.
Privacy rules (hard): local only. A page "What Jarvis knows about me" to read, edit, delete one item or everything, plus a pause-learning switch. Never record keystrokes, screen contents, passwords or other people's messages. Passive tracking of what he does on the PC (which apps, how long) is OFF by default and is only added if the owner explicitly says yes after seeing exactly what would be stored; it shows an on-screen indicator.

### 4.8 Interface
Keep the window and the pill and wire them to the new core through the same message queue. Needed: timer and reminder alerts open the pill, not the window; the knowledge page; notes visible with delete; a clearer "heard / understood / did" trail under "Show details". Mock up any new screen as an artifact first.

## 5. Build order
Each phase ends with Jarvis working, tests green, checklist ticked, notes updated and a commit. V2 lives beside V1 (a new package, for example `jarvis2/`); V1 keeps the desktop icon until V2 is clearly better and the owner says switch.

- **Phase 0, safety net.** Commit V1 and tag `v1`. Harvest the owner's real sentences from `logs/conversation.log` (the "You..." lines) into a labelled test set (Claude labels; list the unsure ones for the owner). Build the evaluation harness (section 6). Record the owner: a 10-minute session where the screen shows each sentence and the recorder saves it: 40+ commands in quiet, with music on the speakers, and with earphones. Keep it local.
- **Phase 1, spikes** (throw-away code that answers the big unknowns with numbers; report in plain words; ask before any download):
  a. Hearing head-to-head: Wisperno-style whole-clip transcription vs V1's pipeline on the recordings. Decides how much listening code is rewritten.
  b. Understanding: V1's way vs "AI picks an ability as JSON + entity matching" on the labelled sentences, with Llama 3.2 3B and candidates.
  c. Media: can the Windows media session control YouTube and others without focus, including previous? Is per-app volume possible?
  d. Memory budget with the chosen models.
  Gate: the owner reads the results and agrees or changes the design.
- **Phase 2, new core skeleton.** Registry, safety, executor, snapshot, event log, harness. Port a first few abilities by wrapping V1 code (open/close/focus app, volume, timers). Gate: harness green.
- **Phase 3, understanding for real.** Resolver, catalog (apps, sites, bookmarks, windows/tabs, files), phonetic matching, clarifying questions, several actions, follow-ups, the reply with its checker. Gate: the owner's labelled sentences right (target to agree after Phase 1; suggestion: 95% or better when the text is heard correctly), replies faithful.
- **Phase 4, ears.** The rebuilt hands-free listening, music and speaker handling, vocabulary biasing. No hold-a-key here. Gate: hands-free solid in live use, x/20 per condition against the V1 baseline, on his recordings and live (proposed bar: 18/20 in each of quiet, music on speakers and earphones; 13.11 false-trigger test passed).
- **Phase 5, the rest of the abilities.** Port everything else and clear the checklist (reminders changed in place, notes, YouTube and media, tabs, time and date, per-app volume, alerts on the pill). Gate: every checklist item ticked with a real test.
- **Phase 6, memory and learning.** L1 to L3, then L4 (L5 if time). The knowledge page. Gate: it learns an alias after one correction and ranks by use.
- **Phase 7, hardening and switch.** Budgets, heat, closing, startup, soak (hours), the full test run including the noisy room, the owner's real-use days, then repoint the desktop icon.

If time runs short, stop after Phase 5 plus L1 and L2: that already gives an understanding Jarvis. Feature freeze: 21 Nov 2026 (the owner agreed). Keep V1 as fallback. Suggested pacing, adjust freely: Phases 0 and 1 in the first two days, 2 to 5 over the next eight or so, 6 and 7 after.

## 6. Testing
- Gold sets kept locally for good: (a) the owner's real sentences with the expected ability and arguments; (b) his recorded audio with the expected text; (c) 30+ multi-turn conversations; (d) unit tests per ability with a fake OS (nothing real opens); (e) misheard-name sets ("prome", "jamin", "crow", "clues file explorer").
- Strict: check the ability, the arguments, the real state afterwards (volume level, timer list) AND the spoken reply. V1 kept passing while the app failed: the reply prompt silently overflowed and errors were swallowed. Never swallow errors: log them, and make tests fail loudly.
- Test through the whole app with the real AI, not only the parts.
- Real-PC checks must not capture the screen beyond Jarvis's own window and must not open or close the owner's real apps (use throwaway windows and files).
- Soak: hours running, hundreds of commands, clean closing, no leftover processes.
- Report numbers (x/20, x/50) per condition, and say what is verified and what isn't.

## 7. Budgets (from CLAUDE.md; measure every phase)
Whole assistant under 4 GB graphics memory; the AI model about 3 GB or less; RAM target 2 to 3 GB; report temperature, CPU and GPU each phase; must not run hot. V1 measured about 3.9 GB graphics memory and 3.5 to 3.9 GB RAM (RAM over target) with the models always loaded. Ideas to measure: load the AI only when needed, a smaller or different recogniser, CPU for what doesn't need the GPU. No offloading models into RAM.

## 10. Risks (honest)
- A model that fits on his laptop has a ceiling; it will still err.
- Graphics memory is already at the limit; any bigger model needs something else to give.
- Windows won't let a background app steal focus; the workarounds are fragile.
- Page-based actions (YouTube links) break when YouTube changes; prefer the media session.
- Hearing is limited by his mic, room and accent, which no rewrite fixes. Phase 1a shows how much is the software.
- Learning from wrong data (teaching a mishearing as a name): learn from explicit corrections or repeated success only.
- Privacy of the learned data: local, visible, deletable, off by default for passive tracking.
- Time: limited, with a hard feature freeze.

### 13.2 Decisions and why
1. **Rewrite the listening loop, keep the same speech model.** The model hears the owner; V1's loop loses whole commands. Mic, room and accent are not the main limit.
2. **Hands-free has no wake model and no early guesses.** Voice detector -> pause -> whole sentence -> Whisper with app names as hint -> for Jarvis only if the name starts the sentence. Name heard 90/90 on the owner's recordings. V1's "Yes, sir" came 0.5 s after the name; here a bare "Jarvis" gets it about 0.8 s after he stops. If the owner minds, Phase 4 may add the wake model only to speed that reply, never as a gate.
3. **Cancel what the PC is playing, using loopback capture.** Takes music from 20/30 to 29/30 without lowering the volume or needing hold-a-key. It should also stop Jarvis hearing itself (unverified).
4. **Hands-free "Jarvis" is the main way in and must be solid first (the owner, 2026-11-03).** Hold-a-key is an optional extra the owner did not ask for: not part of any phase or gate before hands-free passes Phase 4, nothing may depend on it, and hands-free problems (music included) must not be solved by falling back to it. Build it only if time is left before the 21 Nov freeze: same whole-clip route, name not needed, a sensible default key changeable in Settings. Don't ask the owner for a key.
5. **Default AI: Qwen2.5 1.5B Q8 (Wisperno's file, read-only).** Inside the 4 GB limit, fastest, and on real voice the fewest wrong actions (4 against 11 for Qwen 3 4B, small sample). Weak point: asks more. Qwen 3 4B got 18 more of the 265 right but needs 4.31 GB, over the owner's limit. The model is one setting. Phase 3 re-runs both on the finished resolver; if 4B is clearly better with no more wrong actions, the owner decides whether to allow 4.3 GB. Llama 3.2 is dropped; Phi-4-mini and Qwen 3 1.7B are dropped and deleted.
6. **The AI copies words; code does names and numbers.** It got "17 minutes" wrong as a number but right as words. It writes `duration="17 minutes"`, `target="prome"`; code converts and matches.
7. **Short function lines, not JSON, no forced shape.** Forced JSON cost 3x the time (940 vs 290 ms) for the same quality; function lines 115-170 ms. A strict parser checks every line afterwards.
8. **Instant route for one exact shape** (below). Small and declared by abilities, so it can't grow back into V1's pile of patterns.
9. **Names by sound + spelling + usage, no first-letter rule.** jamin, clot, cloud, prome reach the right name; usage and running apps win close calls; below the bar it asks.
10. **Model stays loaded; unload after `ai_idle_unload_min` (default 15) minutes of silence, reload when speech starts.** Replaces "load on demand" from CLAUDE.md: reloading before every command is too slow, and 0.1 s unload saves heat and memory when idle.
11. **Media through the Windows media session; volume per app through Windows audio.** Tested. V1's shared toggle key is gone: play and pause are separate commands.
12. **Not in V1's way:** echo text filters, `_guess`, `rescue`, `misheard_close`, `good_reply` as written, `direct`. Their jobs are covered above.
13. **V2 gets its own database and refuses to run beside V1** (shared named mutex). V1 stays runnable from tag `v1`.

### 13.4 An ability
```python
@ability(name="timer_set", says="start one timer; duration = the user's words. Several timers: several calls",
         required={"duration": Duration()}, optional={}, risk="safe",
         examples=[("keep a ten second timer", 'timer_set(duration="ten second")')],
         phrases=[])
def timer_set(args, ctx) -> Result: ...
```
- Argument types: `Text()`, `Name(kinds=("app","site","bookmark","folder","file"))` (matched in 13.5), `Choice("a","b")`, `Number(lo,hi)`, `Bool()`, `Duration()` (words to seconds, `to_seconds`; no clear number means ASK), `When()` (words to time through timeparse; unclear means ASK).
- `risk`: "safe" runs; "confirm" asks first and needs a yes next turn; anything "never" simply has no ability. The registry IS the allowlist.
- `phrases`: fixed sentences for the instant route, with fixed args: `phrases={"pause": {"action":"pause"}}`.
- `verbs`: optional, for the name shape: `verbs=("open","launch","start","open up")`. Mishearings are added by the alias table, not by code.
- `ctx` holds `snapshot`, `memory`, `os` (real or fake, the only way to touch Windows), `store`.
- Adding an ability: one function in `abilities/`, one test with the fake OS, at most 2 examples, never a sentence from the gold set. Nothing else changes.
- Abilities to start from: the `ABIL` table in `spikes/understand.py`, in its function-line form. Change `timer_set` and `timer_control.which` as in spike. Add `search` browser default rule: Google in Edge unless named. Add `stop_talking` (no arguments): cuts Jarvis's speech off immediately; phrases "shut up", "shut the fuck up", "stop talking", "be quiet", "quiet"; instant route only, never waits for the AI.

### 13.5 The resolver
`resolve(text, snapshot) -> Plan`, in this order, stopping at the first that answers:
1. Strip fillers. **Phrases** exact match; **number shape** `volume N`.
2. **Name shape:** `<verb> <name>[, <name> and <name>]`, every name scoring >= SURE and clear of the runner-up, with no second verb, number, position or "tab" in it (`NOT_A_NAME`). Otherwise go on.
3. **AI**, returning one of: function lines; `ASK: question`; `CHAT: reply`. Prompt: fixed part = rules, ability list built from the registry, examples; changing part = snapshot + last exchange, put LAST so the fixed part stays cached. Temperature 0, max 90 tokens. Before sending, assert prompt + 90 < n_ctx, and fail loudly in the log if not (V1 hid this overflow).
4. **Parse strictly** (`parse` in the spike, Python `ast`): unknown ability or argument, or a bad type, is a parse failure. Retry once at temperature 0.3, then ask him to repeat and log it. Never guess from broken output.
5. **Guards:** a name must really have been said (`spoken_span`) unless the last exchange supplies it; types convert (Duration, When); names match (`decide`): >= 0.8 and clear, or >= 0.6 and clear by 0.08: act; two close: ASK which; nothing: say what was heard and the nearest.
6. **Risk:** "confirm" turns into ASK; the next turn answers it.
```python
Plan: kind "act"|"ask"|"chat"|"ignore"; calls: [Call]; say: str; source "phrase"|"shape"|"ai"; heard: str; raw_model: str; error: str
Call: ability: str; args: dict (converted); spoken: dict (each argument as the user said it, for learning and for "heard/understood/did")
```
A volume change for one app with no direction ("change the volume of YouTube") is ASK: "Louder or quieter, sir?"; it never guesses. Facts questions (clock, counts, lists) must be abilities, so the AI can't invent them. AI chat may never claim an action: replies containing "I've", "done", "opened" etc. with no call get replaced by a plain line.
Ceiling: the owner should expect about 90%, not perfect. Proposed Phase 3 gate (the owner to agree): at least 92% of the clear (not unsure) gold sentences, at most 3% wrong actions, every failure listed. 95% stays the stretch.

### 13.6 Awareness snapshot
Built fresh for each turn (under 50 ms, cached app list), dict:
`now` (date, time, weekday), `apps` (running, by program name), `front` (program + title), `tabs` (best effort, per browser), `playing` (app, title, playing/paused, from the media session), `timers` (length, left, state), `reminders` (text, due; next 8 + count), `notes` (keys only), `last` (last 3 turns: said, ability, result), `mentioned` (last app, tab, timer, note), `profile` (under 200 words). Only a short form goes into the prompt, and only the parts relevant to it; tab titles and note text stay out of the prompt unless asked for. Clock, counts and lists are answered by abilities reading this, never by the AI.

### 13.7 Result and reply
```python
Result: ok: bool; plain: str (a true, complete sentence, always given); facts: dict (names, numbers, what changed); details: str (for "show details"); undo: callable|None; exact: bool (lists, goodbyes: speak plain as is)
```
Reply: if `exact` or the setting is off, `plain`. Otherwise the AI rewords `plain` in the butler voice, in one sentence, from facts only; a checker refuses wording that changes a name or number, swaps next/previous, on/off, flips success, or adds a claim; then `plain` is spoken. `ok=False` always says what failed. An ability must check its real effect where it can (volume read back, process really closed) before `ok=True`. Measure reply time in Phase 3: V1's speech-making adds about 0.65 s when not cached; the action itself never waits for the reply.

### 13.8 Memory tables (SQLite, `data/jarvis2.db`)
```sql
events(id, at, trigger, heard, plan_json, ability, args_json, ok, reply, corrected_by, clip_id)        -- L1: every turn
aliases(heard PRIMARY KEY, name, kind, source, uses, last_at)   -- L2: source = 'correction' | 'repeat'. Learn on one explicit correction, or 3 confirmed successes
usage(name, kind, hour, count, last_at, PRIMARY KEY(name, kind, hour))   -- L2: ranks close matches (replaces the log counts in the spike)
facts(id, key, value, source_event, created, updated)   -- L3
profile(id=1, text, updated)    -- about 200 words, rewritten by the AI occasionally
habits(id, pattern, seen, offered_at, answer)   -- L4: offers only
routines(name PRIMARY KEY, steps_json, created)   -- L5: stored Calls; each step goes through risk checks again
```

### 13.9 Ears
Mic: same opening as V1 (16 kHz mono, default device, 80 ms chunks; follows the Windows default). PC sound: PyAudioWPatch loopback of the default speaker, resampled to 16 kHz.
1. **Canceller** on each 128 ms block (`cancel_echo(live=True)`; delay found by correlation, re-found when the device changes). It learns only when the detector hears no speech, with a 0.8 s hold.
2. **Voice detector** on the cancelled sound (Silero via openwakeword, gain 4, threshold 0.35). Start: keep 0.4 s pre-roll. End: 0.6 s pause. Cap: 12 s. **Noise guard:** if speech stays "on" for over 30 s, skip Whisper until a pause, so it can't run hot.
3. **Whisper** (large-v3-turbo, int8_float16, beam 1, no VAD filter, no previous text, hint = the name + names from the catalog + usage, kept short). Ask for word probabilities in Phase 4; use them only if they measurably help.
4. Hands-free: for Jarvis only if the name starts the sentence (`NAME` + learned spellings). "Jarvis" alone: wake reply, next sentence needs no name for 8 s. After a Jarvis reply, a follow-up needs no name for 8 s.
Speed idea (allowed, only if measured): begin Whisper at 0.3 s of pause and throw it away if speech resumes, so the answer is ready when the 0.6 s pause ends.
Output: `Heard(text, trigger, clip_id, started, ended)`; trigger is "name" or "follow_up". If hold-a-key is ever added (decision 4): clip from press -0.2 s to release +0.3 s, trigger "key".
